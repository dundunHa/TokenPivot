# TokenPivot：个人与团队工作空间模型

> 抓取日期：2026-10-28（UTC）。问题：个人空间是否应永久独立、不可邀请和转换，还是注册时创建可协作的普通工作空间？范围：GitHub、Vercel、Netlify、Supabase，共 4 个产品、8 个官方来源；只研究产品行为，不断言其数据库是否存储类型字段。不实施代码。

## 结论与推荐

1. **建议不持久化个人／团队两种类型：注册创建一个普通工作空间，之后允许邀请。** 对单人开发者和小团队，这同时保留立即使用与原地协作的路径。Supabase 明确采用“注册默认组织＋邀请成员”；Netlify 连单人站点也归团队。[E6][E7] 这是结合 TokenPivot 已给定目标的分析建议，不是经 TokenPivot 用户访谈验证的结论。
2. **不存类型，不等于没有数据归属规则。** 项目、凭证、用量始终属于工作空间；创建者的身份与空间归属分开。成员离开只改变访问资格，不自动带走数据。Supabase 的组织退出要求和 Netlify 的转移后访问规则可作行为参考。[E6][E7]
3. **固定类型有真正价值，但价值是“永久私有区”的承诺，不是方便注册。** 如果产品必须保证每人始终有一个绝不共享、离开任何团队都不受影响的私人账本，则固定个人类型合理。现有背景尚未给出这项承诺；不宜预先承担另建团队、迁移数据和两套限制的成本。
4. **不能把 GitHub 当成“个人不可协作、不可转换”的先例。** GitHub 个人账号可有仓库协作者，也可以转换为组织；同时它的个人账号还是登录身份，与 TokenPivot 工作空间并不等价。[E1][E2]
5. **不要照搬 Vercel 的收费边界和迁移历史。** Hobby 协作需升级是套餐规则，不证明需要永久个人空间类型；文档还保留个人账号转 Hobby team、升级可能需新建团队的路径，不宜描述成所有账号均可无迁移演进。[E3][E4]

## 两种方案的取舍

以下是根据已给定需求推导的设计取舍，不是对 TokenPivot 源码的检查结论。

| 决策标准 | 固定个人／团队类型 | 注册创建普通空间，之后可邀请 |
|---|---|---|
| 单人立即使用 | 自动创建即可，用户无需选类型 | 同样自动创建；无须展示团队概念 |
| 从单人走向协作 | 另建团队；若要沿用原数据，需迁移、复制或重新接入 | 在原空间邀请，项目和历史用量无需换归属 |
| 归属与离开后的可预测性 | 永久私有区更容易承诺；仍须定义团队数据归属 | 规则可统一，但邀请必须明确整个空间的共享范围 |
| 小团队、自托管的复杂度 | 维护个人唯一性、禁止邀请／转换等特殊规则 | 一个空间模型、一套成员规则；私人项目可放另一个未共享空间 |
| T-019／T-020 成本 | 增加类型及限制分支；后续仍需考虑数据迁移 | 初始空间和团队空间共用创建规则；邀请不分类型 |

**核心交换：** 普通空间减少协作时的数据搬迁，但放弃“这个注册空间永远只属于我”的保证。固定类型保住该保证，却把单人项目升级为共同项目变成显式迁移。

### 注册默认与转换规则的核实边界

- **GitHub：** 默认个人登录账号、多组织归属、转换流程均已核实；它不是“个人工作空间永久私有”的直接同类。
- **Supabase：** 默认组织及其邀请规则已核实；在所读文档中，默认组织没有单列不可邀请的特殊规则。无需用户先决定个人／团队类型，即可从默认组织开始。
- **Netlify：** 单人也使用团队、团队成员及多团队规则已核实；**注册是否无条件立即自动创建团队、创建时点，以及所有套餐的邀请限制未核实**。不据此声称所有注册路径完全相同。
- **Vercel：** 注册账号、团队协作与升级规则已核实；**各批次新账号是否都自动获得同一种 Hobby team 未核实**。账号页与 Hobby 页同时出现团队模型和个人账号迁移说明，不能把迁移路径抹去。

## 对 TokenPivot 的建议

1. **T-019：保持一个工作空间模型。** “个人空间创建服务”在产品含义上是“为新用户创建初始工作空间”：创建空间及 owner 成员关系，不赋予永久不可邀请的含义。新建团队空间也是创建普通空间。无需仅为这次选择增加类型字段或转换接口。
2. **T-017：已确认的事务边界不变。** 注册编排在同一事务创建用户与初始空间。不把“注册时创建一次”扩大为“用户一生必须且只能保有一个私有空间”。
3. **T-020：邀请规则统一。** 任一空间由 owner 邀请，member 仍只读。首次邀请时明确提示成员将按权限访问该空间的已有及后续项目／用量；需要保留私人的项目应留在另一未共享空间。只读权限是否允许查看凭证明文，应单独明确，不能从“只读”二字推定。
4. **退出与移除：数据不跟人迁移。** 移除成员撤销其访问；项目、凭证和历史用量仍归空间。阻止移除或退出最后一个 owner。在尚无所有权移交功能时，不必为了本次选择提前加入移交或跨空间转移功能。
5. **界面不强迫理解团队。** 初始显示“我的工作空间”或用户命名；只有一个空间时无需突出切换器。提供“邀请成员”“新建工作空间”，不出现“转换为团队”的必要步骤；也不要用“个人空间”暗示永久不共享。

### 不应照搬

- GitHub 把登录身份与资源命名空间合在个人账号上的历史模型，以及转换账号所需的额外登录账号。[E1][E2]
- Vercel 把协作与付费套餐绑定的规则，以及个人账号转团队会重置部分记录的迁移行为。[E3][E4]
- Netlify／Supabase 的复杂角色、项目级权限、转移与账单重分配机制。它们说明迁移有成本，不说明 TokenPivot 当前就该实现这些功能。[E6][E7][E8]
- 上述云产品的自托管模型：本次未研究其自托管版本，不据此假定它们与 TokenPivot“同一核心支持 SaaS 和自托管”的约束相同。

## 未核实与分歧

- **真正能改变建议的产品问题仍未确认：** TokenPivot 是否承诺一个终身保留、永不共享的私人用量账本？如果是，应优先固定个人类型；如果不是，推荐普通初始空间。竞品做法不能替用户作出这项承诺。
- 没有访谈 TokenPivot 用户，也没有真实使用数据证明“多数用户想把全部个人历史直接共享给团队”。普通空间的优势只对愿意在原空间继续协作的用户成立。
- Netlify 默认建团队时点、Vercel 新旧账号默认团队一致性如上标为未核实。已尝试官方站点检索并读取账号／套餐文档；部分 Vercel 搜索返回 `Codex search request failed (HTTP 500)`。达到 8 个来源后停止，不补推断。
- 不从“普通组织／团队的产品行为”反推这些产品底层没有类型字段；本报告对 TokenPivot 不存类型的建议是成本与需求取舍。

## 方法

- 对照维度：注册默认身份／空间、单人到协作的路径、成员与转换规则、多空间归属、退出及数据归属。
- 按产品划分 4 个取证子问题，每个产品读取 2 个官方来源；最终综合为第 5 项分析，不增加外部来源。总计 4 个产品、8 个一手来源，未扩大到 Linear／Sentry。
- 本次是产品规则比较，不是参考代码实现；未克隆仓库、未读取 TokenPivot 业务代码，未将官方功能描述当作用户需求调查。
- 来源通过官方站点搜索定位，使用 curl 获取完整正文。日期按页面更新日期或抓取日期记录；没有证据的注册流程差异明确保留为未核实。
- 停止条件：8 个来源预算用完，已足以比较模型，剩余不确定项不影响识别需要用户确认的“永久私有”承诺。
