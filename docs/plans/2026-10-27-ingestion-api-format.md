## 1. 目标、范围与非目标

目标：形成首版同步批量采集接口的唯一格式依据，冻结方法/路径、格式版本、字段与校验、缺失/零值/估算语义、规范化与摘要、逐项结果、时间窗口、批量限额，并记录供 T-023 使用的查询结构限额。实施时只写接口文档，T-011 按文档实现，不再各自选择格式。

非目标：

- 不实现 handler、认证、存储、聚合、清理、插件或查询 API；不改业务代码、DDL、配置和依赖。
- 不核实 T-043 的平台能力，不断言 DSH/PI 已能提供某字段；来源没有能力时按格式报告缺失或不支持，不能伪造请求事件。

- 不定 T-023 的筛选、分组、时区、游标和具体查询路径；本任务只给它共同限额。
- 不引入异步队列、207 异步入队语义、通用版本注册框架、请求频率限制器或新依赖。首版没有峰值和并发量测，不承诺吞吐。

## 3. 拟冻结的采集格式

以下除“已确认 Q1–Q3”标注外，均为推荐直接定稿的接口设计；它们是**本计划提案，不是现行已发布接口**。

### 3.1 方法、路径、认证与版本

- `POST /api/v1/ingestion/events`，请求和响应均为 UTF-8 `application/json`。
- URI 中 `v1` 就是**外部格式主版本**，请求体不再放第二个 `format_version`，避免两个版本值不一致。不兼容的字段删除、类型/含义变化、必填项增加、规范化语义变化或新逐项状态，必须升级主版本；旧版本在仍有合法重传时不得直接退役。
- `normalization_version` 是服务端生成并持久化的比较算法版本，不由客户端提交；它与 URI 主版本相关但不是同一个字段。
- 接入凭证按 T-010 的 header 方案认证。`workspace_id`、`source_id`、凭证 ID 和 `received_at` 不允许出现在事件载荷中，身份只从认证和服务端处理结果取得。
- 客户端必须忽略新增响应字段；服务端拒绝未知请求字段，以便发现拼写错误和越权字段。新增请求字段若会被旧服务端拒绝，须按兼容性规则发布，不能称为无条件兼容。

### 3.2 请求外壳与事件字段

```json
{
  "events": [
    {
      "source_event_id": "request-123",
      "project_id": null,
      "provider": "example-provider",
      "model": "example-model",
      "occurred_at": "2026-10-27T07:00:00-07:00",
      "usage": {
        "input_tokens": {"value": 100, "quality": "known"},
        "output_tokens": {"value": 20, "quality": "estimated"},
        "cache_read_tokens": {"value": 60, "quality": "known"},
        "reasoning_tokens": {"value": 8, "quality": "known"}
      },
      "status": "success",
      "duration_ms": 1250
    }
  ]
}
```

上例只展示字段形状，不证明任何平台实际能提供这些值；省略的 total 按 §3.3 推导为 `{"value":120,"quality":"estimated"}`。

| 字段 | 首版规则 |
|---|---|
| `events` | 必填数组，保持输入顺序；空数组整批拒绝。数量上限见 Q2。 |
| `source_event_id` | 必填 UTF-8 字符串，1–256 个 UTF-8 字节；不透明、逐字节比较，不做大小写、空白或 Unicode 归一化；拒绝 NUL 和控制字符。同一稳定 source 内不得复用。T-009 开工时仍须验证实际上限与索引项兼容。 |
| `project_id` | 可省略或为 null，均表示“未归属”；非空时接受带连字符 UUID，大小写均可，存储和比较统一为小写。非法、跨空间或不可用项目必须拒绝，不能降为 null。项目生成/注册规则仍属 T-044。 |
| `provider`、`model` | 各为必填 UTF-8 字符串，1–128 字节；拒绝空值、首尾空白和控制字符；保留大小写，不做别名合并、trim 或 Unicode 归一化。 |
| `occurred_at` | 请求最终完成时刻，不得用采集、上传或接收时间替代。必填 RFC 3339 时间字符串，必须带偏移；允许最多 6 位小数秒，拒绝超精度、闰秒和没有偏移的本地时间。解析后统一为 UTC 微秒。 |
| `usage` | 必填对象；允许所有指标都缺失，因为最终请求仍可能已发生但没有可用用量。六个指标见下节。 |
| `status` | 可省略或为 null；非空为 1–64 字节 UTF-8 字符串，首版不透明保存，不发明平台状态映射。 |
| `duration_ms` | 可省略或为 null；非空为 `[0,2^53-1]` 的 JSON 整数，0 是真实零，null 是未知。 |

Token 和 `duration_ms` 使用 JSON number 的十进制整数形式，不接受字符串、小数、指数或负零；上限 `2^53-1` 是首版可移植性格式边界，不是对平台最大用量的实测。所有字符串长度按 UTF-8 字节而非字符数校验。

事件内未知字段产生该项永久拒绝；外壳未知字段、任何层级重复 JSON 键或无法无歧义解析的 JSON 使整批在写入前拒绝。重复键不能依赖所用 JSON 库“最后一个值覆盖”的偶然行为。

### 3.3 用量值、零、缺失、估算与子集

六个指标固定为 `input_tokens`、`output_tokens`、`total_tokens`、`cache_read_tokens`、`cache_write_tokens`、`reasoning_tokens`。每个指标只用一种结构：

- `{"value":N,"quality":"known"}`：实测或来源确认的真实值；N 为 `[0,2^53-1]` 整数，包含真实零。
- `{"value":N,"quality":"estimated"}`：估算值，N 同样必填且非负；估算零不等于实测零。
- `{"value":null,"quality":"missing"}`：缺失；整个指标省略与此规范形式等价。
- 其他组合均无效：known/estimated 不得缺值，missing 不得带数值，不允许额外质量词。每指标独立判断，禁止用一个全局质量标记覆盖全部字段。

归一化规则：

1. `cache_read_tokens`、`cache_write_tokens` 是输入子集，`reasoning_tokens` 是输出子集，不另加到 total。父项和子项均为 known 时，子项大于父项则该项永久拒绝；涉及 estimated 时不因大小关系不成立而拒绝；父项缺失时不据子项反推父项。
2. 输入和输出均有数值且省略 total 时，由服务端按两者之和补出 total；两者均 known 时推导质量为 known，否则为 estimated。显式 total 保留其独立值和质量；仅当输入、输出、total 均为 known 时，total 不等于两者之和才拒绝。涉及 estimated 时不因精确等式或质量不同而拒绝。例如输入 estimated 100、输出 known 20、total known 120 合法；父项 estimated 50、子项 known 60 不因大小关系而拒绝；三项均 known 且输入100、输出20、total130 则非法。
3. 输入或输出至少一个缺失时，可保留来源提供且口径可比的 total 及其质量；不能从 total 反推输入/输出，也不能把唯一已知分量当成完整 total。
4. 加法或字段值超出 `2^53-1` 为永久 `USAGE_OVERFLOW`，不截断、不转浮点。
5. 全部指标缺失仍可接受最终请求事件并计事件数，但所有用量显示不可用；这不是零用量事件。

### 3.4 规范化、摘要和跨版本比较

首版 `normalization_version = "tokenpivot-usage-event/v1"`，摘要为 SHA-256 的原始 32 字节，不存十六进制大小写不同的文本。首版只实现这一套算法，不建算法注册系统。

规范化比较集合固定为：

1. occurred_at（UTC、固定 6 位小数秒）；
2. project_id（小写 UUID 或 null）；
3. provider、model；
4. 六个指标各自的 value 与 quality，包含由输入/输出补出的 total；
5. status、duration_ms（缺省统一为 null）。

排除 workspace/source 的认证表示、内部事件 UUID、source_event_id 身份本身、received_at、凭证、请求下标、JSON 字段顺序和对象空白。身份已由唯一键确定，重传改变身份字段不是同事件内容修正。

文档须给出固定顺序的规范化 JSON 数组、六个指标的完整对象（省略项显式补成 missing）、无空白序列化、精确字符串转义规则，以及至少四组“规范化文本 + SHA-256”测试向量：偏移等价、字段顺序等价、真实零与 missing 不同、estimated 与 known 不同。规范化和落库必须使用同一份类型化结果。

版本规则保持最小：

- 同版本先比较 SHA-256；相同为 duplicate，不同为 conflict。
- 不同版本不得直接比较摘要。只有能由实际留存列无损重建某一共同版本的全部比较字段时，才重建该版本规范化内容并比较。
- 若有损升级使共同版本无法重建，必须明确返回永久 `NORMALIZATION_INCOMPATIBLE`，不能误报 duplicate 或 conflict；旧客户端仍走原 v1 路径重传，直至事件超过 180 天窗口。未来版本只有在书面说明映射和兼容限制后才能发布，本任务不预建双哈希或保存原始报文。

### 3.5 逐项响应与错误

已完整解析并处理的批次统一返回 HTTP 200，不用 HTTP 207。这里的 accepted 是原始事件和分钟增量已同步提交，不是“已入队”；逐项业务拒绝不代表整个 HTTP 请求失败。

```json
{
  "request_id": "opaque-server-generated-id",
  "results": [
    {"index": 0, "status": "accepted"},
    {"index": 1, "status": "duplicate"},
    {"index": 2, "status": "conflict"},
    {"index": 3, "status": "expired"},
    {"index": 4, "status": "rejected", "error": {"code": "INVALID_ARGUMENT", "message": "invalid event"}},
    {"index": 5, "status": "retryable", "error": {"code": "UNAVAILABLE", "message": "temporarily unavailable"}}
  ]
}
```

- `results` 与输入 events 等长、按输入顺序排列，`index` 从 0 开始；不能只按 source_event_id 组装，否则同批重复 ID 会覆盖结果。
- `accepted`：本项已确认提交；`duplicate`：同身份同内容且没有新增计数；`conflict`：同身份不同内容，永久拒绝；`expired`：先于查重的超期拒绝。
- `rejected` 用于其他永久项错误，必须带稳定 error.code：`INVALID_ARGUMENT`、`FUTURE_EVENT`、`PROJECT_INVALID`、`USAGE_UNSUPPORTED`、`USAGE_OVERFLOW`、`NORMALIZATION_INCOMPATIBLE`。
- `retryable` 用于可安全按原身份重试的本项失败，必须带 `UNAVAILABLE`、`INTERNAL` 或 `DEADLINE_EXCEEDED`。Commit 结果不明也只能用 retryable，不能写 accepted 或声称已回滚。
- 所有响应都有不透明 request_id；message 只供人读，不作为分支依据，不包含 SQL、堆栈、凭证、事件原文或跨空间资源信息。

整批错误采用 `{ "error": { "code", "message", "request_id", "details" } }`，details 仅用于安全的字段/原因列表：

| 情况 | HTTP / code | 写入与客户端动作 |
|---|---|---|
| JSON 无法解析、重复键、外壳字段/空数组/条数错误 | 400 / `INVALID_ARGUMENT` | 无写入；修正请求，不盲目重试。 |
| 凭证缺失或无效 | 401 / `UNAUTHENTICATED` | 无写入；按 T-010 更新凭证。 |
| 已认证但无采集权限 | 403 / `PERMISSION_DENIED` | 无写入；不自动重试。 |
| 请求体超过字节上限 | 413 / `BODY_TOO_LARGE` | 无写入；拆小批次。 |
| 非 `application/json` | 415 / `UNSUPPORTED_MEDIA_TYPE` | 无写入；修正 Content-Type。 |
| 无法在开始前形成任何逐项结果的服务端/依赖故障 | 500 / `INTERNAL` 或 503 / `UNAVAILABLE` | 用原身份重试；不能据此断定没有已提交项。 |

处理期限到达时，若仍能写响应，已处理项给出真实结果，未开始项全部给 `retryable/DEADLINE_EXCEEDED`，不凑 accepted；若连接已断开或响应失败，客户端重传整个原批次，由唯一身份消除重复。

### 3.6 时间精度、时钟偏差与采样点

- 存储和规范化精度均为 UTC 微秒；输入超过 6 位小数秒一律拒绝，不舍入或截断。`2026-10-27T14:00:00Z` 与 `2026-10-27T07:00:00-07:00` 规范化后相同。
- **Q1 推荐时钟偏差为 0**：有效区间保持已确认的 `[T-180×24h,T]`，两端包含；下界之前是 expired，上界之后是 `rejected/FUTURE_EVENT`。不得把未来时间截成 T，也不得用 received_at 替换 occurred_at。
- 推荐 0 不是性能判断，而是为了不改已确认的 received_at 180 天保留关系。若允许未来偏差 S，晚到清理时可能出现记录仍处在可补报窗口却被按 received_at 删除的情况；要支持 S，必须同步修改 ADR-0002/0003、清理截点以及 T-009 的 `occurred_at <= received_at` 不变量，不能只在上传入口加宽判断。
- 服务端 T 使用数据库实际当前时间，不用事务开始时间常量；每项首次判断前采样，在 INSERT、冲突 SELECT、分钟增量锁等待之后及 Commit 前重新采样复核。不得以批次起点的一次采样覆盖整个长批次。
- received_at 是首次接受事务中显式采样的服务端接收时间，不是精确 Commit 墙钟时间；重传不更新。Q1 为 0 时继续满足 `occurred_at <= received_at`。
- 文档至少给出下界恰好、下界前 1 微秒、T 恰好、T 后 1 微秒、不同偏移等价、超精度和等待后跨过下界七组例子。

### 3.7 批量与查询限额（Q2/Q3 已确认采用以下推荐值）

推荐采集限额：每批最多 100 项、请求体最多 1 MiB、从 handler 开始最多 8 秒处理预算。8 秒小于现有 10 秒 WriteTimeout，用于尽量留下逐项响应时间，但不是吞吐保证；超过条数/体积是整批拒绝，超过处理期限按上节返回未处理项。首版不另建进程内或分布式的每秒请求数（RPS）限制器。

推荐查询结构限额，由 T-023 写入具体查询接口并由 T-028 消费明细分页边界：

- 历史统计最多查询 13 个日历月且不得早于实际保留截点；统一 `[start,end)`，带秒的历史范围明确拒绝，不静默对齐。
- 每次趋势查询最多 1000 个时间桶；超过时返回稳定 `TOO_MANY_POINTS`，附允许上限和 T-023 支持的粒度中满足上限的最细建议粒度；没有可用粒度时提示缩短范围，不服务端静默改粒度。分组返回数量由 T-023 另定并计入响应大小设计。
- 请求明细分页默认 50、最大 200；明细仍受 180 天实际数据保留限制，不能因分钟统计有 13 个月就承诺明细可查 13 个月。
- 不定查询 RPS/并发数。PRD 的并发查询量和性能环境尚未确认，在没有量测前写数字只会形成虚假保证。

## 4. 与 T-011、T-023 及其他前置任务的边界

| 任务 | 责任边界 |
|---|---|

## 6. 验收标准

1. 任一事件字段都能回答：是否必填、类型、字节/数值范围、缺省含义、是否参与规范化；workspace/source 无法由载荷伪造。
2. 真实零、估算零、missing、仅提供 total、输入/输出可推导 total、缓存/推理子集均有合法与非法示例；不存在“缺失当零”或子集重复累加。
3. occurred_at 的偏移等价、微秒精度、超精度拒绝、180 天下界和上界均有可执行测试向量；Q1 与保留/清理关系一致。
4. 同批重复 ID 的响应仍与输入等长且下标稳定；accepted、duplicate、conflict、expired、rejected、retryable 的重试和持久化含义与 ADR/T-011 一致。
5. 格式版本、规范化版本、同版本摘要、跨版本无损重建及不可重建时的明确错误均已写清；旧 v1 重传不因当前实现升级而被误判。
6. 数量、体积、处理期限、查询桶数、明细分页上限与超限动作完整；没有未经验证的 RPS 或吞吐承诺。
7. 所有摘要向量经实际计算复核，OpenAPI 结构经只读评审；T-011 可直接把示例转成 handler/service 测试，T-023 不需要重新决定共同限额。
8. 实施 diff 只有 `docs/openapi/openapi.yaml`，没有代码、迁移、依赖或其他文档改动。

## 8. 用户确认记录

用户已选择以下三项推荐值；本节保留推荐理由，不表示仍待决定。

1. **时钟偏差**：推荐 **0 秒**，维持 `[T-180×24h,T]` 和现有 180 天 received_at 保留不变量。若要求允许未来 S，必须同时批准调整保留截点和相关 ADR，不能只在采集入口放宽。
2. **采集限额**：推荐 **100 项/批、1 MiB/请求、8 秒处理预算**。这些是首版安全上限提案，未经过 TokenPivot 压测；实施后若要收紧，对合法旧客户端属于不兼容变化。
3. **查询结构限额**：推荐 **最多 1000 个时间桶、明细分页默认 50/最大 200**；历史统计最多 13 个日历月沿用 ADR-0003 既定保留规则，不重新开放保留策略决策；超限明确报错并建议粒度，首版不定 RPS/并发数。

三项参数已确认，规划阶段完成；实施需要另行授权。接口文档最终定稿须满足 §5 的 T-010 认证格式交接条件。

## 9. 风险与未核实项

- 所有限额和每日约 10 万事件规模都没有本轮负载测试支撑；参考项目的默认 100 不是 TokenPivot 的性能证据。
- 严格的未知字段和数字规则便于防错，但意味着新增请求字段、放宽后又收紧等变化必须做兼容性评审。
- 跨版本规则依赖比较字段持续落列；未来若有损删除信息，不能靠哈希或“版本不同”伪装成正确判定。
- 本任务未核实平台字段能力，也未证明所有 source 都能提供稳定 ID、最终用量或完成时间；这些能力缺口不得由服务端补造。
- 本轮只写计划，未创建/校验 OpenAPI、未计算摘要向量、未运行测试或连接数据库。
